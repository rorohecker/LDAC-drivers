## Code rundown

| Component | Responsibility | Assessment |
|---|---|---|
| `vendor/libldac` | Sony encoder, compiled through `ldaclib.c` and `ldacBT.c`, which include the algorithm sources | Real published implementation, not an approximation |
| `core/encoder.cpp` | Buffers 128-sample PCM blocks, calls libldac, adds RTP/LDAC headers, advances timestamps/sequences, drains final frames | Offline comparison passes for supported formats |
| `core/avdtp.cpp` | Endpoint discovery, negotiation, stream state, partial peer-command handling | Protocol and timeout defects reproduced |

| `driver/driver.c` | KMDF Audio Sink profile transport, two L2CAP channels over Windows Bluetooth BRBs | Startup contract violation; lifecycle not validated |
| `windows/capture.cpp` | WASAPI loopback capture and conversion to 48 kHz stereo S16 | Discontinuities terminate capture; no endpoint switching |
| `windows/main.cpp` | File/loopback playback, producer thread, pacing, adaptation, startup retry | Data race, timing issues, no live reconnect lifecycle |

| `tools/*.ps1` | Build, identify hardware, generate/package/sign/install/smoke/uninstall | Build works; uninstall failure reproduced |

Audio path: PCM file or WASAPI capture → application queue → Sony encoder → RTP/AVDTP → our KMDF transport → existing Windows Bluetooth radio stack → XM5. The Intel radio driver is not replaced.

There is no dedicated Windows playback endpoint. Replacing the XM5 Audio Sink service driver displaces inbox A2DP for that service without providing a normal replacement audio device. Loopback captures another playback endpoint and can leave local speakers audible.

## Sony source and rebuild verification

Compared every vendored file with AOSP revision [`eeee1a3f5f8df1282e3a6d297085885fd886737b`](https://android.googlesource.com/platform/external/libldac/+/eeee1a3f5f8df1282e3a6d297085885fd886737b/).

All 32 files differ in raw bytes because of checkout line endings. After CRLF/LF normalization, 28 match exactly. Four contain source changes:

- `src/bitalloc_sub_ldac.c`: conditional removal of GCC's unused attribute for MSVC; trailing blank line.
- `src/struct_ldac.h`: conditional empty `UNUSED_ATTR` for MSVC; trailing blank line.
- `src/ldacBT_internal.h`: excludes unused/unavailable `unistd.h` on MSVC.
- `src/pack_ldac.c`: unsigned shift avoids shifting a negative signed integer.

`vendor/LOCAL_CHANGES.md` documents only the last change; its provenance notes are incomplete. LICENSE and NOTICE match upstream after line-ending normalization.

Separately rebuilt upstream using only the three necessary MSVC syntax/header adaptations, retaining its original packing arithmetic. Compared that library with the local library using identical wrapper/compiler settings:

- Four inputs: silence, distinct left/right tones, deterministic full-range noise, and opposite-sign channel impulses.
- HQ, SQ, MQ; MTUs 679, 1024, 4096.
- Two seconds per case, including drain; fixed RTP seeds exercise sequence/timestamp wrap.
- **36/36 emitted packet files have identical SHA-256 hashes.**

This supports equivalence of the local changes on these vectors and this compiler. Both sides use our packetizer, so this does not independently validate AVDTP/RTP. It does not establish equivalence to every Sony device, private firmware, compiler, or input. No reference decoder, official conformance vectors, perceptual comparison, or real XM5 receiver was used.

Our integration exposes only **48 kHz, stereo, signed 16-bit PCM**, with 990/660/330 kbps modes. It does not expose 44.1/88.2/96 kHz, 24-bit audio, or the full codec API. LDAC is lossy. Upstream `abr/` is not included; our adaptive policy is a separate implementation. A complete Sony audio-stack reproduction cannot be claimed.

Evidence: [source hashes/diffs](artifacts/audit-20260919/provenance.json), [packet comparisons](artifacts/audit-20260919/encoder-comparison.json).

## Confirmed defects and runtime risks

P1 means fix before recommending hardware use. P2 means material reliability/performance/compatibility work. Reproductions use user-mode harnesses, not a loaded kernel driver.

### F1 — P1: unnamed device receives a security descriptor

`driver/driver.c:189–201` sets `FILE_DEVICE_SECURE_OPEN`, then calls `WdfDeviceInitAssignSDDLString`. It neither assigns a device name nor sets `FILE_AUTOGENERATED_DEVICE_NAME`. Microsoft requires one before assigning SDDL. This is a confirmed API-contract violation and expected startup blocker; the exact runtime error has not been observed here.

Fix: request an autogenerated name before assigning the intended ACL, then verify AddDevice/Prepare/interface creation. [Microsoft contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdfdevice/nf-wdfdevice-wdfdeviceinitassignsddlstring).

### F2 — P1: normal signaling timeout can end playback

`windows/main.cpp:97` polls signaling before each media packet. `windows/transport.cpp:7–10` converts every failed IOCTL into a numeric message such as `Driver IOCTL failed, Windows error 121`. `core/avdtp.cpp:185–189` recognizes idle timeouts only by searching for the text `timeout` or `Timeout`. Numeric timeout errors therefore escape and terminate playback, potentially before the first packet.

Reproduced with error messages for Windows codes 121 and 1460 through the actual Session implementation. These are injected error cases, not evidence of which status this adapter returns. Microsoft documents that an expired ACL receive timeout completes with an error.

Fix: preserve error codes or use typed timeout results; only known receive timeouts should be nonfatal. [ACL timeout contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/bthddi/ns-bthddi-_brb_l2ca_acl_transfer).

### F3 — P1: data race in adaptive loopback

The producer modifies the queue under `mutex` at `windows/main.cpp:133–135`. The consumer unlocks at line 148 and reads `queue.bytes()` at line 149. The same non-atomic byte counter is concurrently writable, creating a C++ data race when those operations overlap.

Fix: capture queue depth while holding the mutex. This is a source-level finding; AddressSanitizer does not detect data races and ThreadSanitizer was not run.

### F4 — P1: uninstall crashes before package deletion

`tools/uninstall-test.ps1:16–20` uses `$matches` as an accumulator. PowerShell is case-insensitive, and regex `-match` overwrites it through automatic `$Matches`. The next `+=` fails: `A hash table can only be added to another hash table.`

Reproduced using the actual script in memory, mocked `pnputil`, and synthetic `oem99.inf`. Zero mock delete calls occurred; no real uninstall was attempted.

Fix: use a distinct variable name and exact package identification. English `Published Name:` parsing also needs a localization-safe replacement; deletion failures should propagate reliably.

### F5 — P1: failed-close and teardown ownership are unresolved

`driver/driver.c:44–59` retains the handle after a failed close. IOCTL CLOSE nevertheless reports success at line 124. ReleaseHardware at lines 174–178 dereferences the profile interface even if closes failed. Prepare does not clear or resolve those stale slots before reuse. This can block reopening and leaves channel/callback ownership unresolved across stop/remove/restart.

The driver has synchronous lower requests on one sequential queue, no explicit pending-request cancellation/rundown state machine, and a Bluetooth callback pointing into device context. Device-level WDF synchronization does not automatically cover every external callback. A WDM device reference is not a demonstrated proof of correct callback rundown.

These are concrete lifecycle gaps; a use-after-free or bugcheck has **not** been demonstrated. Fix requires explicit ownership and power/removal transitions, cancellation, close-error reporting, and callback rundown, followed by approved Verifier and hardware stress. [WDF synchronization boundaries](https://learn.microsoft.com/en-us/windows-hardware/drivers/wdf/using-automatic-synchronization).

### F6 — P2: AVDTP responses/endpoint validation are wrong

Reproduced with remote SEID 2 and local SEID 1:

- `core/avdtp.cpp:124–126`: GetConfiguration incorrectly prefixes two endpoint IDs; its response should contain capabilities only.
- Lines 120–145: commands for a local endpoint also accept the remote endpoint number. The existing fake uses identical IDs and hides this.
- Lines 77–79: a generic one-byte error cannot represent all rejections. Start/Suspend rejection requires failing endpoint plus error; SetConfiguration/Reconfigure also need a service-category field.
- Start/Suspend validate only the first endpoint in a list and accept a subsequent invalid endpoint.
- Empty Abort terminates the active stream instead of being rejected/ignored as malformed.

Additional review concerns: unknown/unsupported commands use the same rejection format; command lengths and reserved bits are not consistently validated. Peer-initiated setup and incoming L2CAP connection handling are missing.

Fix: command-specific validation/serialization and independent endpoint IDs in tests. [Independent AOSP/Bumble implementation and specification references](https://android.googlesource.com/platform/external/python/bumble/+/bc23d3a7f382bc24762218bb4aa4578821dcc105/bumble/avdtp.py).

### F7 — P2: congestion observations cancel each other

`windows/main.cpp:111` reports send time with zero queue depth; line 149 separately reports queue depth with zero send time. A high-backlog observation followed by a fast send resets the congestion counter. Reproduced 100 such cycles at 30,000 queued bytes: quality stayed HQ.

The 150 ms soft threshold versus 200 ms hard limit gives limited recovery time. Queue-path `set_quality` failure is ignored and requested/accepted quality can diverge.

Fix: coherent observations containing both measurements, a stable observation interval, accepted-quality tracking, and tested hysteresis. This remains distinct from Sony ABR.

### F8 — P2: pacing produces late sends and bursts

`windows/main.cpp:95–115` uses `sleep_until`, lacks multimedia scheduling/high-resolution timing policy, and rebases only after being over 100 ms late. Smaller delays can cause back-to-back sends. A synchronous signaling poll precedes each media send, with all driver operations serialized.

A short probe of the same scheduling primitive, without Bluetooth or audio, produced:

| Mode | Intended interval | p99 wake lateness | Largest gap | Gaps under 1 ms, of 199 |
|---|---:|---:|---:|---:|
| HQ | 5.333 ms | 11.03 ms | 16.17 ms | 14 |
| SQ | 8 ms | 12.41 ms | 17.05 ms | 13 |
| MQ | 16 ms | 11.21 ms | 28.72 ms | 0 |

This is not a universal Windows bound or headset latency measurement. It shows that meeting the packet interval cannot be assumed. Fix scheduling/catch-up policy and separate asynchronous signaling from media, then measure real send timing under load. [Results](artifacts/audit-20260919/timing-results.jsonl).

### F9 — P2: pauses and disconnections are not recovered

- `windows/main.cpp:98–103`: waiting for peer Resume allows capture to fill the 200 ms queue. A long pause ends capture; producer failure is not checked inside that wait loop.
- `windows/capture.cpp:48–49`: any discontinuity after the first packet stops capture.
- `windows/main.cpp:82–88`: `--reconnect` retries initial Session startup only. Transport construction errors and later streaming disconnects are outside that retry loop.
- Capture stays on the startup endpoint. Capture timestamps/device positions are discarded; no long-term clock-drift correction exists.

Fix: explicit pause/drop/reset semantics, an outer reconnect lifecycle with fresh transport/encoder state, endpoint-change handling, and drift measurements.

### F10 — P2: large-file memory and malformed WAV handling

`windows/main.cpp:70–74` reads the whole PCM/WAV input into RAM. One hour of PCM needs about 691 MB before overhead. `core/wav.hpp:23,36` allocates using untrusted chunk lengths before validating actual file size/format. Allocation exceptions can bypass manual FILE cleanup. RIFF boundaries and format consistency are incompletely validated; Windows `long` limits large unknown-chunk seeks.

Fix: streaming reads, bounded allocations, format/container validation, RAII, and malformed-file tests. This is user-mode reliability risk, not demonstrated kernel corruption.

## Processing overhead and latency

Release measurements include codec, wrapper copies/buffering, packet allocations, RTP construction, and measurement bookkeeping. They exclude WASAPI, pacing, Bluetooth/kernel work, and headset decoding. Each mode encoded 120 seconds of deterministic full-range noise three times, in 10 ms PCM blocks at MTU 1024. Input generation was outside the timed region.

| Mode | Median equivalent realtime demand, one CPU core | Median trial p99 per 10 ms block | Largest observed block | Peak benchmark working set |
|---|---:|---:|---:|---:|
| HQ | 0.25% | 54.3 microseconds | 342.5 microseconds | 4.41 MiB |
| SQ | 0.20% | 70.5 microseconds | 1.171 ms | 4.53 MiB |
| MQ | 0.23% | 93.8 microseconds | 588.1 microseconds | 4.42 MiB |

CPU demand is process CPU time divided by represented audio duration, not whole-machine Task Manager utilization. These are approximate short G16 trials; they do not establish Acer performance, energy consumption, DPC/ISR load, or worst-case execution time. The working set belongs to the benchmark, not a complete streamer. Differences between modes are not a general claim about their relative cost.

Normal HQ/SQ/MQ packets contain 2/3/6 frames of 128 samples, corresponding to 5.33/8/16 ms and approximately 187.5/125/62.5 packets per second. Final drain packets can contain fewer frames. The 13-byte RTP/LDAC headers add about 19.5/13/6.5 kbps before lower Bluetooth overhead.

Encoding appears inexpensive; scheduling and blocking transport are larger concerns. Each media packet adds a signaling-receive and media-send IOCTL using a full 4,112-byte structure, plus BRB/request allocation and copies. Their real CPU and power overhead remains unmeasured.

The 200 ms PCM queue is a capacity limit, not an end-to-end latency guarantee. Capture, codec lookahead/aggregation, queue occupancy, scheduling, radio retries, and headset buffers contribute separately. The 100 ms send-stall check only runs after the send returns. No acoustic latency, delay reporting, or real media timing telemetry has been measured.

Evidence: [raw performance](artifacts/audit-20260919/performance.json), [benchmark implementation](artifacts/audit-20260919/benchmark.cpp).

## Other limitations and existing safeguards

- Fixed-width IOCTL structures, packet/version/channel/timeout validation, METHOD_BUFFERED, exclusive access, intended administrator/SYSTEM ACL, and headset-address matching are useful safeguards. The ACL/interface are not hardware-verified.
- Binding is restricted to the XM5 Audio Sink, never the Intel radio. A model/service HWID can match more than one headset of that model; the client selects by Bluetooth address.
- Channel flags do not explicitly request authenticated/encrypted L2CAP. Pairing may already provide it; enforcement needs verification before making link-security claims.
- All macros in `driver/xm5_trace.h` are no-ops, including the WPP-enabled branch. No actual WPP/ETW provider exists.
- `pnputil /add-driver /install` success is not evidence of winning driver ranking or starting. Boot-state text parsing is locale-dependent.
- The INF advertises early Windows 10 despite DIRID 13 requiring a later build (previous InfVerif warning). KMDF 1.33 and fixed SDK/WDK 28000 impose further compatibility/build constraints. Binaries are x64 only.
- README status is stale about Windows compilation. Existing tests use a textual `fake timeout` and equal local/remote endpoint IDs. The labelled collision test does not inject a collision. Unit-test counts should not be interpreted as hardware coverage.

2. Correct AVDTP command handling and congestion observations; cover pause/resume and full reconnect behavior.
3. Implement explicit kernel request/callback ownership, cancellation, failed-close handling, and power/removal rundown; add real diagnostics.

5. Rebuild, repeat comparisons/sanitizers, review lifecycle changes, and package/sign the reviewed result.
6. On an explicitly approved test machine: confirm its XM5 Audio Sink HWID, load the driver, obtain a matching real `smoke-info` PASS, and obtain user confirmation of audible PCM.

Full certainty cannot follow from an offline audit. These findings justify withholding an installation recommendation even though the encoder comparison passed. Phase 0 hardware smoke, Phase 1 audio, and Phase 2–5 hardware/endpoint/WHQL milestones remain incomplete.
